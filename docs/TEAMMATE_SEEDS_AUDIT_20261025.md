## 2. 表格实际说明了什么

- 26个种子：0–4、42、300–319。只有0、42有该表直接列出的基础平台成绩，分别0.25、0.41。
- `good`仅是**固定偏置后、六个无标签房间等权预测分布**的TV≤0.25，共11个；不应称为11个已验证高准确率模型。
- `collapsed`仅是同一统计口径下预测0人的比例>40%，共10个。没有U真值，宜称“高判0倾向”，不能单凭这个比例证明预测错误。
- 两类有重叠：seed311，b_TV=0.243，同时b_p0=40.2%。因此不是11好+10坏+5其他互斥分组；实际10个仅good、9个仅高判0、1个两者都有、6个两者都没有。
- “d1平均64%判0”经CSV重算为64.2615%，但这是**加固定偏置后**的跨种子平均，并非d1识别错误率。其他房间分别h1=29.91%、i1=34.52%、j1=28.91%、u1=27.27%、v1=20.59%。这些为重新汇总CSV，不是本次重新跑2900窗。
- 六房间等权比例不是2900窗按窗口汇总比例；不能混用。
- 表中“均匀”是假设下的诊断。平台常量预测探针各约0.20，为公开评测类别接近均衡提供线索，但不足以证明每个U房间都五类均匀。

## 4. 复现配方仍然缺什么

YAML与checkpoint配置确认了结构、五轮、采样预算、优化器等显式参数，但包内没有训练程序、缓存内容/校验、窗口顺序或环境清单，不能独立确认“除了seed全部相同”。checkpoint中的cache=std只是缓存标识，不是精确数据清单。

README中“baseline是否有额外增广待确认”已经有答案：**原始forward内有增广**，包括幅度/相位噪声、频率mask、MixStyle、route dropout和普通Dropout。配置文件没列出，不等于训练没执行。队友复现是否执行了完全相同路径，还需要其运行源码确认；不能反过来断言他们没用这些增广。

原run也是seed42。这与新seed42权重不同，不是发现了矛盾，而是提示仅凭seed和简化配方不足以定位原run。原始代码从历史特征银行读取数据，当前整理脚本从raw重新算特征，这也是已有证据支持的实现差别。

队友README里缺的seed、确切数据、增广和final.pt已在 `handoff/run037_20261025/`及D盘交接zip准备好。原始检查点SHA256为：

## 5. 这批权重下一步如何使用

1. 保留原始0.54作为控制。先把26个底座与原0.37放在统一的**实际ONNX预处理/输出**口径下比较，缓存原始输出；标注来源与U分开。
2. 优先比较seed42（已有0.41）和310（固定偏置后d1判0仅18.8%、总体TV=0.157），以seed0为高判0对照。308虽然TV最小，但d1判0仍71.2%，所以不因总体均匀就选308做主力。以上是研究优先级，不是新冠军判断。
3. 先检查与原底座在记录/房间上的分歧和有标签来源的纠错/破坏；这些全量权重已看过48条标签，来源正确率不构成泛化证明。
4. 新底座各自校准，再比较有/无条件TTA。共用校准流程，不直接共用原底座的五个偏置或保护阈值。
5. 若开发比较显示互补，才试有条件的少量专家融合；不重复已失败的无差别平均。26个全量checkpoint不能当作留房间模型，需要另行训练房间隔离的代理实验，才能较可信地筛选新规则。
